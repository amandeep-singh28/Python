->VPC Fundamentals
It stands for virtual(It is not physical) private cloud.
Inside AWS we create our own network.
Along with the infrastructure, AWS provides us private cloud which helps us to deploy our EC2 instances.

If server would be in same place, than there will be no security, anyone could access them, No privacy.
Using VPC each customer gets their own network inside AWS, their own IP address(range) and their own security.

->CIDR + IP Addressing 
Whenever u r creating your VPC, u need to decide your ID address range
10.0.0.0/16 -> This is called CIDR notation

10.0.0.0 -> Starting address
16 -> Size of network
Lesser the number(after /) -> Larger network
More the number(after /) -> Smaller network

->Subnet
Smaller network inside VPC
Inside AWS you created VPC and inside VPC there is Subnet.
There is a big organization so you have stored the data on VPC and in organization there are various department so those departments represents Subnet.


Subnet: 10.0.1.0/24

- Total IPs = 256
- AWS reserves 5 IP addresses
- Usable IPs = 251

Reserved IPs:
- First IP (network address)
- Second IP (VPC router)
- Third IP (DNS)
- Fourth IP (reserved by AWS)
- Last IP (broadcast)

->How to create your VPC
Search VPC
Create VPC
Give it a name(VPC-Test-1)
IPV4 CIDR(10.0.0.0/16) -> 65K around IP address
Rest on default.

Then Create a subnet for VPC-Test-1
Give this (10.0.0.0/24)

/16 creates around 65,536 IP addresses in the VPC.

When we create a subnet with /24, it means that a block of 256 IP addresses 
(from that /16 range) is allocated to that subnet.



****AWS VPC Networking (Public Access to EC2)****
-VPC
Create a VPC named "TEST"
IPV4 CIDR - 172.16.0.0/16

Now we need subnets inside our "TEST" VPC
Give a subnet name "SUBNET TEST"
IPV4 CIDR - 172.16.0.0/24

Now create a EC2 instance named "EC2/Test1"
Under network settings, give the VPC(TEST) and Subnet(SUBNET TEST)
Enable the auto assign public IP(We want access from the public site)
Give a rule(Type- HTTP and Source type- Anywhere)

This will throw an error because there is no connection to the EC2. That's why we required Internet Gateway and Route table

To fix this error, do the following things:
-Creating IGW(Internet Gateway)
Go to VPC, Create IGW named "Test/IGW"

Now you are required to connect these together(IGW and route table)
Go to route table, Create a route table name Route/Test, Select "Test" VPC
So, this route table has been create for your VPC but there are no subnets associated with it.
So, you required EC2 subnet association with the route table.
Go to route table, Select Route/Test, Go to Subnet Association, Edit Subnet Association and select "Subnet Test", Save association.
Now go to IGW, you will see "Test/IGW" is currently detached. Click on Internet gateway ID, Click on Actions, Attach to VPC, Select "TEST".
Now you also need to connect the route table with Internet gateway because any traffic which comes through the IGW will be routed towards your VPC. Go to route table, Edit routes, Give 0.0.0.0/0(Means whole internet), Select Internet Gateway and your current IGW.

****VPC Peering (Connecting Two VPCs)****
Create another EC2 instance like we have create before named "EC2/Prod"

Test/VPC -> 172.16.0.0/16
Prod/VPC -> 192.168.0.0/16

Test IP -> 172.16.0.125
Prod IP -> 192.168.0.222

Now, if you will try to ping another EC2/Prod in EC2/Test, this will not work because we have not yet connected the both instances.

ping 192.168.0.222 (Type this command in EC2/Test) -> Nothing will happened

->Solution
Go to VPC, there will be an option "PEERING CONNECTIONS".
Go to Create Peering Connection named "Test-Prod-Peering"
Now we are going to make a request from "Test/VPC" and acceptor is "Prod/VPC"
VPC ID(Requestor) -> Test/VPC
VPC ID(Acceptor) -> Prod/VPC
After this we are required to accept this connection because anyone can request. Go to action and accept the request. Now the connection is made between the two VPCs.
Now do you think, the connection is made now??
If you will try again to ping Prod on EC2/Test. You will still not get connected. This is because, we also need to update our security groups.
We have not allowed the traffic from Test/VPC and Prod/VPC(We have allowed the traffic from SSH and HTTP).
Go to EC2/Prod and add the security group, "ALL ICMP-IPV4" and give IP as 172.16.0.0/16" which is your Test/VPC IP.
Similarly do it for EC2/Test.

Now, you also need to connect configure ROUTE TABLES
Go to Test/VPC route table, Add route 192.168.0.0/16, Peering Connection
Go to Prod/VPC route table, Add route 172.16.0.0/16, Peering Connection

Now run the command "ping", CONNECTION SUCCESSFUL

****About Policies****
It is divided into 4 main parts:-
(i)Effect
It decides whether you have given the access or not.
If you allow permission it is granted else not granted.
It is written in JSON format
{
    "Effect" : "Allow" -> You have allowed the user to have the access
}

(ii)Action
It defines what operations are allowed like read, delete, update and add data.
You are telling just what action to be done.
Example:-
GetObject -> Read
PutObject -> Add

{
    "Effect" : "Allow",
    "Action" : "s3:GetObject"
}

(iii)Resource
It tells us what object we are accessing, which object you are performing operations on.

(iv)Condition
We are just putting some conditions.
Example:-
Under what conditions access is allowed(Only during office hours)

{
    "Effect" : "Allow",
    "Action" : "s3:GetObject",
    "Resource" : "arn:aws:s3:::my-bucket/*",
    "Condition" : {
        "aws.SourceId" : "192.168.1.1"
    }
}

****How can we create these policies in AWS****
Click On IAM, policies, Create Policy, Click on JSON, and add this data.

{
    "Version": "2012-10-17",
    "Statement": [
    {
        "Effect": "Allow",
        "Action": "s3:GetObject",
        "Resource": "arn:aws:s3:::my-bucket/*"
    }
]
}

Attach the policy to the user, Go to the user, click on LPU, Add Permission, Attach policies directly and search for it "s3ReadOnlyPolicy".
Now that particular user can only read.

Click on particular policy, you can also see the JSON format for that policy

->Some Rules
If you see Deny in policy
Deny will always win over any allowed function

Permission can come from multiple places. If any policy says deny the final answer is always deny.

If in User Policy -> Deny and Group Policy -> Allow than always DENY will get followed.
If a user has two policy and one policy says deny, DENY will be followed.

->Different types of policies
(i)Managed Policy vs Inline Policy
You create them once, you can attach them to multiple users, groups and roles.
Inline policies they are directly attached to one user, and are not usable. It can used only once. These are only for one person or one user.

(ii)AWS Managed vs Customer Managed
These policies which are managed and created by AWS are called as AWS managed policies.(Ready Made policies which are already made in AWS but you don't have much control over the policies)
Customer Managed policies are created by us like we created above using JSON. You have full control over the system.

->User vs Roles
-User is a full time like permanent access(Teacher).
-It is a Temporary Identity like no permanent access(Student). It is used for shorter tasks. It has expiry time 

->Important Point
Roles can be assigned to services. If you attach a role to EC2, EC2 gets Temporary access. If we will not give then there will be a possibility for data leakage.

"IAM Roles can be attached to services like EC2 to provide temporary credentials. This avoids hardcoding access keys, which improves security and reduces the risk of credential leakage."

****IAM Roles for EC2 (Accessing S3 without Credentials)****
Go to IAM, click on roles, Create role, which entity you want to create role - temporary rights(Click AWS Service), Choose EC2, Click Next.
Which permission that role can have, Select amazons3readyonlyaccess.
Give role name and create role

When we try to log in to an account, we require credentials.  
Similarly, when accessing S3 (storage), credentials are required.  

Here, we have created a role which provides temporary access.  
This role gives read-only access permission to EC2 to access S3.  

When you attach this role to EC2, it can access S3 without manually using credentials, because AWS automatically provides temporary credentials.  

If we do not use a role, then we would need to use access keys (credentials), which is not a secure practice.

->Important Point(About Instance Profile)

Instance profile acts as a bridge between them.

Instance profile are automatically connected. That instance profile you need to connect with your EC2.
